INTRODUCTION                                        *extensions-introduction*

extensions.nvim recreates the UX of VSCode's "Extensions" sidebar tab inside
Neovim: browse a catalog of Neovim plugins, search/filter it, view details,
and install or remove plugins with a keypress. It manages plugins through
lazy.nvim, using its own spec file so it never touches other config files.

==============================================================================
REQUIREMENTS                                        *extensions-requirements*

- Neovim >= 0.9.0
- lazy.nvim         (https://github.com/folke/lazy.nvim)
- nui.nvim          (https://github.com/MunifTanjim/nui.nvim)

==============================================================================
SETUP                                                      *extensions-setup*

Add it as a lazy.nvim plugin spec, e.g. in `lua/plugins/extensions.lua`: >lua
    return {
      "DevDanielAlvarez/Extensions.Nvim",
      dependencies = { "MunifTanjim/nui.nvim" },
      cmd = "Extensions",
      opts = {},
    }
<
`opts = {}` triggers `require("extensions").setup(opts)` automatically. You
may also call it yourself:
>lua
    require("extensions").setup({
      catalog_path = nil, -- see |extensions-configuration|
    })
<
==============================================================================
COMMANDS                                                *extensions-commands*

                                                                  *:Extensions*
:Extensions             Opens the extensions panel.

==============================================================================
MAPPINGS                                                *extensions-mappings*

`:Extensions` opens a centered floating window: a search bar and plugin
list on the top-left, a live details preview on the top-right that updates
as the cursor moves, and a keymap reference panel docked along the bottom
-- all visible from the moment it opens.

    i           Install the plugin under the cursor.
    x           Remove the plugin under the cursor.
    c           Configure the plugin under the cursor (if it has options).
    /           Focus the search bar and filter live as you type.
    <Tab>       Cycle status filter: All / Installed / Not installed.
    r           Reload the catalog and re-render the list.
    q / <Esc>   Close the extensions panel.

Inside the config popup opened by `c`:

    <CR> / <Space>   Toggle a `toggle` field, or edit an `int`/`string` field.
    q / <Esc>        Close the config popup.

==============================================================================
CONFIGURING A PLUGIN                                *extensions-plugin-config*

Catalog entries may declare a `config` field: an array of option specs a
plugin supports. Pressing `c` on an **installed** plugin that has one opens
a popup with one line per option: >lua
    {
      key = "check_ts",           -- option name written into that plugin's opts
      input_type = "toggle",      -- "toggle" | "int" | "string"
      input_name = "Treesitter-aware pairs", -- label shown in the popup
      default = true,
    }
<
Changes save immediately into that plugin's entry in
`lua/plugins/extensions-nvim.lua`, as an `opts = { ... }` table -- a
first-class `lazy.nvim` spec field it already knows how to pass to
`require(x).setup(opts)`. Configuring a plugin that isn't installed yet is
refused (install it first); most plugins only apply `opts` once at load
time, so changes may need `:Lazy reload <plugin>` or a restart to take
effect -- extensions.nvim notifies you of this after saving.

One key name is special: a `toggle` field with `key = "enabled_default_keymaps"`
is never written into `opts` (most plugins would ignore an unknown option
there anyway, but it isn't a real one, so it's kept out). Instead, when set
to `true`, the catalog item's `default_keymaps` field -- raw Lua source for
a `keys = { ... }` lazy.nvim spec block, since keymaps carry functions that
JSON can't represent -- is spliced verbatim into that plugin's spec entry
as a `keys = { ... }` field, alongside `opts`. Setting it back to `false`
removes the block again. This is how catalog authors ship a plugin's
documented default keymaps as a one-toggle opt-in.

==============================================================================
CONFIGURATION                                      *extensions-configuration*

                                                    *extensions-catalog_path*
catalog_path ~
    Type: `string?`, Default: `nil`
    Path to a JSON file (same shape as the bundled `data/catalog.json`)
    with a custom list of catalog items, overriding the small bundled
    catalog. Each item must have the shape: >json
        {
          "repo": "user/repo",
          "name": "display name",
          "description": "...",
          "category": "...",
          "tags": ["tag1", "tag2"],
          "config": [],
          "default_keymaps": null
        }
<
    `config` is optional; see |extensions-plugin-config| for its shape.
    `default_keymaps` is optional too: raw Lua source for a `keys = {...}`
    block, only needed if `config` includes an `enabled_default_keymaps`
    toggle (see |extensions-plugin-config|).
